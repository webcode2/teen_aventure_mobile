# Query and scalability audit — 18 October 2026

## Verified issues and fixes

- **Parent memberships:** six sequential top-level Prisma reads became three independent reads in parallel. A single ClassGroup relation filter covers owned, assigned and child-linked groups. PostgreSQL returns each class once instead of sending duplicate sibling enrollments and a growing child-ID parameter list. Read-only parent permissions and private join codes are preserved. Counts now consistently count approved participants.
- **Group detail / leaderboards:** class authorization and peer masking share one access result. Class metadata is reused for detail rendering. Tests enforce one metadata read and one assignment check, with unrelated and pending memberships denied. Score aggregation filters through database membership relations instead of serializing every member ID into an IN clause. Full rosters remain available, as requested.
- **People directory:** the dashboard requests one entity/page, searches and filters in PostgreSQL, and does not paginate full directories in browser memory. Page size is validated (maximum 100; UI uses 40), ordering has an ID tie-breaker, stale search responses cannot overwrite newer results, and search requests are debounced. Scores are summed only for displayed explorers. Staff/pastor screens no longer fetch every child/family/score. Older callers without a kind parameter are capped at 500 records per entity and receive legacyLimit metadata.
- **Active-user chart:** distinct identities and all six rolling activity windows are aggregated in PostgreSQL. The endpoint transfers six counts instead of downloading a year of score/device rows and scanning them six times in Node. User/child identity prefixes and window semantics are preserved.
- **Progress:** repeat score-history references are grouped in PostgreSQL before transfer. Existing completion, step and Sunday-hold semantics are unchanged.
- **Achievements:** explorer reads use bounded concurrency (four explorers), ordered results, and request-local promise caching, so siblings share in-flight leaderboard work. No shared authorization/data cache is introduced. Empty owner sets skip unnecessary group and streak reads.

## Database verification and indexes

A read-only pg_indexes inspection of the configured database confirmed missing reverse relation indexes on Child.familyId, Child.transitionedToUserId, Guardian.userId, ChurchRole.userId, ClassAssignment.teacherUserId and ClassEnrollment.childId. The existing compound uniqueness constraints generally start with the opposite key. This catalog inspection changed no user records, scores or database schema. The new active-window SQL was also executed against synthetic CTE fixtures in PostgreSQL: duplicate identities, user/child identity separation and all six windows returned the expected counts without persisted data or schema changes.

Migration `20261018154000_query_access_indexes` adds 17 ordinary B-tree indexes for those relation filters, class/status rosters, class ministry lookup, recent child/family score activity, rolling activity windows, and deterministic directory ordering. Prisma schema validation passes. **Applied to the configured database.** PostgreSQL catalog verification confirms all 17 indexes match the intended tables/column order and are valid and ready. Prisma reports the database schema is up to date. Before deployment, an old failed `20261015090000_quest_week_completion` history record blocked the runner; its complete table, column types/nullability/defaults, primary/foreign keys and indexes were verified against the migration SQL, then its history was reconciled as applied without rerunning quest DDL or changing quest records. Index creation can lock writes while building; for future large live deployments use a maintenance window or an operator-reviewed concurrent-index rollout.

## Validation limits and remaining scale considerations

Unit and component tests cover page bounds/filtering, displayed-child-only sums, query reuse, membership authorization/privacy, completion behavior and bounded achievement fan-out. No database-reset integration suite or seed was run against the existing database.

This audit does not claim a latency percentage or production capacity. Catalog row estimates are too small/stale for meaningful load conclusions. With the indexes deployed, collect p50/p95 timings, connection-pool wait time and EXPLAIN (ANALYZE, BUFFERS) on representative staging data.

Very large rosters still return all participants to preserve the requested product behavior; cursor-paginated boards and incremental mobile rendering are the next step if groups grow into thousands. Deep directory pages use offsets, and substring search uses case-insensitive contains: at large directory sizes, evaluate cursor navigation and pg_trgm indexes or a search service from measured plans. Achievement queries are bounded in concurrency but still grow with the number of linked explorers. A score rollup would reduce repeated all-time ledger sums at higher activity volumes, but requires transactional backfill/reconciliation and has deliberately not been introduced without data verification.
